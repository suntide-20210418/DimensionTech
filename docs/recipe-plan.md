# DimensionTech 配方方案（已实现）

> 落点：`datagen/ModRecipesProvider`，49 条模组配方（**全部有序合成**）+ 1 条原版材料便利配方。验证链全绿：`compileJava` → `runData` → `test` → `processResources --rerun` → `runGameTestServer`（91/91）→ `clean build`。

---

## 一、最终决策

| 项 | 决策 |
| --- | --- |
| 一键搭建 | **消耗材料**（服务端扣背包，全或无，跳过已正确的位，遇阻挡中止） |
| 无升级方块 | **删除**该方块；12 个升级位改由「采掘器外壳」填充 |
| `StructureMinerUpgradeBlock.Type.NONE` | **保留枚举值**（四处索引算运依赖它占 0 号位） |
| 碎片作合成材料 | 可以。反应堆的碎片是催化剂、提交时原样退回，正常路径净消耗 **0** |
| 数据整合器 | 2 级阶段（吃 2 级碎片+代币） |
| 结构阐释器 | 5 级阶段（吃 5 级碎片+代币） |
| 精华桶 | **不加配方**，空桶右键反应堆取液 |
| 升级方块 | 每级都吃**同级碎片 + 同级代币**（专精与聚合一致） |
| 核心 | 一级采掘器 ×1；聚焦6 标志材料 ×2/份 |

无配方项（结构采掘器产物）：维度解构核心、维度碎片 ×6、采掘代币 ×6、附魔印记；精华桶 ×5。

## 二、驱动全部配方的两条规则

1. **碎片 N / 代币 N 只能由 Tier N 采掘器产出**（`ExpectationRewardGenerator.addTieredRewards`，每周期 `min(10, parallel)`）。因此"搭 Tier N 矿机所需材料的依赖闭包"绝不能含碎片 N / 代币 N：
   - **聚焦方块链**只能从上一阶上转（且聚焦方块必须与矿机同阶，`StructureMinerMultiblock.isComplete:132-135`）；
   - **采掘器控制器**只能吃 `碎片(N-1)` + `代币(N-1)`；
   - **只有升级方块**吃自己这一阶的碎片/代币 —— 因为 12 个升级位也接受外壳，而外壳是纯原版料，所以首台矿机不依赖任何机器产物。
2. **真实门槛是能量（4^n 到 1,048,576 FE/t）、结构探索与反应堆流体链**，所以材料造价刻意压在廉价原版料上。

## 三、配方总表（49 条模组配方 + 1 条原版材料便利配方）

### A 级 · 入口工具（3 条）

| 输出 | 类别 | 输入 |
| --- | --- | --- |
| 结构标记器 ×1 | 有序 | 铁锭×4、石英×1、玻璃×1、紫水晶×2、红石×1 |
| 数据整合器 ×1 | 有序 | 碎片2×2、石英×1、紫水晶×2、外壳×1、代币2×2、红石×1 |
| 结构阐释器 ×1 | 有序 | 碎片5×2、石英×1、外壳×1、数据整合器×1、钻石×1、代币5×2、末影珍珠×1 |

```
数据整合器              结构阐释器
碎片2   石英    碎片2    碎片5   石英     碎片5
紫水晶   外壳    紫水晶    外壳    数据整合器  钻石
代币2   红石    代币2    代币5   末影珍珠   代币5
```

> 整合器读「玩家已探索结构」，阐释器读「游戏中全部结构」（直接跳过探索），故分别后移到 2 级与 5 级。两者都是可选强化插件，不在必需路径上，后移不产生死锁。
> 两者都是**有序**配方，格数上限 9，所以原版填充料（玻璃/荧石粉）被砍掉，把格子留给「碎片N×2 + 代币N×2」这道进度门槛。

### B 级 · 骨架（2 条）

| 输出 | 类别 | 输入 |
| --- | --- | --- |
| 采掘器外壳 ×8 | 有序 | 铁锭×4、玻璃×2、石砖×2 |
| 采掘器结构方块 ×1 | 有序 | 石英×2、紫水晶×4、铁锭×1、红石×2 |

> 一台矿机需 **44 外壳**（32 框 + 12 升级位）+ 8 聚焦 + 1 结构方块 = 6 次外壳合成（铁 24 / 玻璃 12 / 石砖 12）。

### C 级 · 维度聚焦方块（6 条，1:1 上转）

| 输出 | 输入 | 标志材料 |
| --- | --- | --- |
| 聚焦1 ×4 | 铁锭×4、红石×2、玻璃×1 | — |
| 聚焦2 ×4 | 聚焦1×4、紫水晶×2、玻璃×1 | `amethyst_shard` |
| 聚焦3 ×4 | 聚焦2×4、荧石粉×2、玻璃×1 | `glowstone_dust` |
| 聚焦4 ×4 | 聚焦3×4、末影珍珠×2、玻璃×1 | `ender_pearl` |

| 聚焦6 ×4 | 聚焦5×4、核心×2、玻璃×1 | `dimension_deconstruction_core` |

```
聚焦1                    聚焦N (N=2..6)
铁   红石  铁            聚焦(N-1)  标志     聚焦(N-1)

### D 级 · 机器本体（8 条）

| 输出 | 类别 | 输入 |
| --- | --- | --- |
| 结构数据操作仪 ×1 | 有序 | 外壳×2、玻璃×1、紫水晶×2、铁锭×1、金锭×2、红石×1 |
| 结构反应堆 ×1 | 有序 | 黑曜石×4、外壳×2、紫水晶×2、荧石粉×1 |
| 第1阶采掘器 ×1 | 有序 | 铁锭×2、结构方块×1、外壳×2、石英×2、**核心×1**、红石×1 |
| 第N阶采掘器 ×1（N=2..6） | 有序 | 外壳×4、碎片(N-1)×1、聚焦N×2、采掘器(N-1)×1、代币(N-1)×1 |

```
操作仪                  反应堆                     采掘器1
外壳  玻璃  外壳         黑曜石 外壳    黑曜石       铁锭   结构方块 铁锭
紫水晶 铁锭 紫水晶       紫水晶 荧石粉  紫水晶       石英   核心     石英
金锭  红石  金锭         黑曜石 外壳    黑曜石       外壳   红石     外壳

采掘器N (N=2..6)

聚焦N      采掘器(N-1)  聚焦N

> **控制器必须用 (N-1) 级碎片/代币**：用同级就意味着"先有 Tier N 矿机才能造 Tier N 矿机"，硬死锁。第 1 阶用核心承接探索门槛（箱子 5% + 20 箱硬保底）。链路：
> `一级矿机 → 碎片1 → 反应堆(水) → 结构精华 → 二级矿机 → 碎片2 → … → 六级矿机`

### E 级 · 升级方块（30 条）

**专精升级（24 条）** — `efficiency` / `parallel` / `luck` / `energy`

| 输出 | 类别 | 输入 |
| --- | --- | --- |
| `upgrade_{type}`（tier1）×4 | 有序 | 外壳×2、签名材料×2、碎片1×2、代币1×2 |
| `upgrade_{type}_tier_N` ×4 | 有序 | 外壳×2、签名材料×2、碎片N×2、代币N×2 |

```
外壳   签名   外壳
碎片N  签名   碎片N
代币N  ─      代币N
```

签名材料 ↔ 反应堆操作物品一一对应（顺手教会反应堆规程）：

| type | 中文 | 签名材料 | 呼应状态 |
| --- | --- | --- | --- |
| `efficiency` | 效率 | 石英 | branch |
| `parallel` | 并行 | 紫水晶 | recurse |
| `luck` | 幸运 | 荧石粉 | converge |
| `energy` | 能量 | 红石 | stabilize |

**聚合升级（6 条）**

| 输出 | 类别 | 输入 |
| --- | --- | --- |
| `upgrade_aggregate_tier_N` ×2 | 有序 | 四种专精(N) 各×1、碎片N×2、代币N×2 |

```
PLE      P=并行  L=幸运  E=效率   D=能量
FDF      F=碎片N  T=代币N
T T
```

> 聚合 tier6 = 90/90/−7/90/150，专精 tier6 = 120/120/−30/120/300。单块聚合约值 2.2 个专精块，而槽位固定 12 个 → 聚合是「槽位效率」选项；4 专精 → 2 聚合，值得一做但不碾压专精。

### F 级 · 原版材料便利配方（1 条）

| 输出 | 类别 | 输入 |
| --- | --- | --- |
| 紫水晶碎片 ×4 | 无序 | 紫水晶块 ×1 |

> 原版只允许碎片→方块、不允许反向分解，而本模组每一阶都在吃紫水晶碎片（聚焦链 + 专精升级签名材料），没有这条就难以批量获取。刻意做成**有损**（9 个碎片压成的方块只还原 4 个），不可能靠它循环刷取。
> 落在 `data/minecraft/recipes/amethyst_shard.json` —— 结果物品是原版物品，`RecipeProvider.save` 用结果物品的注册名当路径，所以自动进原版命名空间，与本模组改造前的行为一致。

## 五、随本次一起修掉的既有问题

1. **`processResources` 打包阻断**：`ModBlockStateProvider` 的 `tier == 0 ?` 硬编码分流导致 tier_2 手写模型与 datagen 占位模型重名，`processResources` 报 `duplicate` 直接失败。已改为按「已手写模型的 tier 集合」判断（`Set.of(0, 1)`），并删除残留的生成占位文件。
2. **`ModRecipesProvider` 里的占位配方**：`紫水晶块 → 紫水晶碎片×4` 与本模组无关，已删除（连带其 advancement）。
3. **一键搭建原本是免费建造**：`StructureMinerMultiblock.place` 只做 `setBlock`，生存模式点一下凭空生成 53 个方块，所有多方块材料成本都被架空。现已改为服务端按投影扣料。

## 六、遗留（不在本次范围）

- **附魔印记**：`EnchantmentMarkConverter.convert` 全库无调用点，`EquipmentDismantler` 只还原主材料、丢弃附魔 → 印记当前既无生产路径也无消费路径。补法是在 `ExpectationRewardGenerator.generate` 的 dismantle 之后补一次 convert（行为变更，需 GameTest）。注意换算是指数的（等级 L → 2^L 个），`MAX_MATERIALIZED_MARKS`(65536) 上限会整批回退。
- **`Type.NONE` 枚举值**已不可达，可后续单独提交清理（需同步改 4 处索引算运）。
- 一键搭建的**背包扣料路径**目前只有投影/阻挡/幂等三类的 GameTest 覆盖；实际扣背包需要玩家 fixture，未自动覆盖。
